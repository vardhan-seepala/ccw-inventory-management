Request lifecycle, end to end

One filter change, five hops. This is the shape every page in the app follows — some pages skip a step or two, noted in §04.

01 · UI FilterBar.vue User changes a <select>, mutates a shared ref
02 · state useFilters.js Module-scope refs act as a de facto global store — no Pinia
03 · client api.js Builds URLSearchParams, calls :8001/api/* via axios
04 · server main.py Filters in-memory lists, validates response via Pydantic
05 · render computed() View re-derives aggregates, template updates reactively

The filter system — who actually honors what

Four filters live in useFilters.js and render once in FilterBar.vue above every page. But only two endpoints implement all four server-side — the rest either drop a dimension or filter entirely in the browser.

"client" rows fetch the full unfiltered dataset once, then re-derive a filtered view inside a Vue computed() — no refetch happens when the filter changes.

04

Three concrete traces

The same filter, three different amounts of work done by the server versus the browser.

Dashboard — full server round-trip

Select "Tokyo" → selectedLocation ref mutates → Dashboard's watch([...4 refs], loadData) fires → Promise.all hits getDashboardSummary, getOrders, getInventory, getBacklog → FastAPI's apply_filters() + filter_by_month() run against the in-memory lists → Pydantic validates the typed responses → four raw refs update → statusData, topProducts, categoryData computeds re-derive → charts redraw.

Inventory — one dimension silently dropped

Inventory.vue's watch list omits selectedPeriod and selectedStatus on purpose — loadInventory() only ever sends warehouse + category. The backend route doesn't declare month/status params at all, so even a stray query string would be ignored. Net effect: Time Period and Order Status visibly do nothing on this page — by design, not a bug.

Demand / Backlog / Spending — client does the filtering

These three endpoints take zero query params. Each view fetches the entire dataset, separately fetches /api/inventory with the active warehouse/category to build a valid-SKU allowlist, then a computed() intersects the two in the browser (Array.filter(item => validSkus.has(item.item_sku))). Spending.vue takes this furthest: its period watcher is a literal no-op — watch([selectedPeriod], () => {}) — because every derived value already re-filters via string-matching YYYY-MM against order_date/date inside computed properties.

05

Known gaps

Things the frontend calls or renders that the backend doesn't back — found by reading both sides, not by running into them.

404s

Tasks & purchase orders aren't implemented server-side. api.js defines getTasks / createTask / deleteTask / toggleTask and createPurchaseOrder / getPurchaseOrderByBacklogItem, targeting /api/tasks* and /api/purchase-orders*.

main.py has no matching routes. App.vue's loadTasks() catches the failure and falls back to mock tasks from useAuth.js — degrades gracefully, but silently.

missing component

PurchaseOrderModal.vue is referenced but doesn't exist. Dashboard's openPOModal/handlePOCreated toggle showPOModal and render <PurchaseOrderModal> in the template — it's never imported or registered. Triggering that path throws Vue's "failed to resolve component" warning.

dead route

Backlog.vue is unreachable. The file and its logic are complete, but main.js's route table never mounts it and no nav link points to it.

style outlier

Reports.vue breaks every project convention at once: Options API instead of Composition API, direct axios calls with a hardcoded URL instead of going through api.js, and no awareness of the shared filter state at all.
